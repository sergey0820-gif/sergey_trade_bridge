# Design: margin/ГО-aware sizing в calc_quantity_from_risk()

Статус: **дизайн-документ, реализация не начата**. Основа для отдельной,
неспешной сессии — не трогать `calc_quantity_from_risk()` в бою до
прохождения плана тестирования и dry-run периода ниже.

Контекст: `calc_quantity_from_risk()` (`trade_executor.py:580-629`) считает
объём позиции только от риска по стопу (`qty = risk_rub / (R * lot_size)`),
не проверяя, хватит ли реального ГО/маржи на фьючерс. Реальный инцидент:
BRU6, 2026-08-04, `INVALID_ARGUMENT 30042: Not enough assets for a margin
trade` — заявка отклонена брокером постфактум, не заранее. См.
`STRATEGY.md` "Открытые вопросы" п.4.

---

## а) Точная спецификация

**Данные**: ставка ГО на фьючерс — `initial_margin_on_buy`/
`initial_margin_on_sell` (MoneyValue, рубли на лот), поле уже используется
в этой сессии (`futures_lot_check_fixed.py`, задача Б point-value фикса).
Получать тем же паттерном, что уже написан для `_is_crypto_futures_candidate()`
в `auto_executor.py`: `client.instruments.future_by(id_type=INSTRUMENT_ID_TYPE_UID,
id=uid)` → `resp.instrument.initial_margin_on_buy` / `.initial_margin_on_sell`
(выбор buy/sell по стороне сделки long/short).

**Изменение сигнатуры и логики**:

```python
def calc_quantity_from_risk(
    entry: float,
    stop_price: float,
    lot_size: int,
    capital: float,
    risk_per_trade: float,
    go_per_lot: float | None = None,      # НОВОЕ: ГО на 1 лот, ₽. None — акция или ГО недоступно
    available_margin_headroom: float | None = None,  # НОВОЕ: свободный запас маржи, ₽
) -> int:
```

**Логика** (после текущего расчёта `qty_float`/`qty`):

```python
if go_per_lot is not None and available_margin_headroom is not None:
    max_affordable_qty = int(available_margin_headroom // go_per_lot)
    if max_affordable_qty < 1:
        logger.error(
            "ГО не позволяет открыть даже 1 лот: доступно %.2f₽, нужно %.2f₽/лот — вход отменён",
            available_margin_headroom, go_per_lot,
        )
        return 0  # 0 — новый сигнал "нельзя войти", отличать от текущего fallback "1 лот"
    qty = min(qty, max_affordable_qty)
```

**`available_margin_headroom`** — берётся из `client.users.get_margin_attributes()`
(та же функция, что уже вызывает `auto_executor.py::get_margin_utilization()`),
считается ВНУТРИ `trade_executor.py` независимо, так как это отдельный
подпроцесс без общего состояния с `auto_executor.py` (см. п. "риск
рассинхрона" ниже) — `headroom = liquid_portfolio * MAX_MARGIN_UTILIZATION -
starting_margin`.

**Изменение возвращаемого значения**: текущая функция всегда возвращает
`>= 1` (fallback "1 лот" при ошибке). Новая логика вводит осмысленный
**0 = "нельзя войти"** — вызывающий код (`main()` в `trade_executor.py`)
должен явно проверять `quantity == 0` и отменять вход (аналогично уже
существующей проверке `already_open_position`), а не молча пытаться
разместить 0-лотовый ордер.

## б) Акции — не ломаем, ветвление по типу инструмента

Акции (`class_code == "TQBR"`) не имеют концепции ГО в этом смысле (другой
механизм — `klong`/`kshort`). Вызывающий код (`main()`) должен передавать
`go_per_lot=None` для акций **всегда**, независимо от условий рынка —
никакой автоматической эвристики "похоже на фьючерс/акцию по цене". При
`go_per_lot is None` — функция ведёт себя **побитово идентично** текущей
(старый код-путь не трогаем, просто оборачиваем его в `if`). Регрессионный
тест на это — первый в списке тестов ниже.

## в) План тестирования (mock, до касания боевого кода)

По аналогии с `test_defense_in_depth_crypto.py` (5 сценариев, mock
`client.instruments.future_by`) и фиксом `dynamic_stop_manager.py`
(тестировали через мок раньше, чем коммитили — там мок поймал ВТОРОЙ баг,
которого не было бы видно без теста):

1. **Регрессия акций**: `go_per_lot=None` → результат идентичен старой
   формуле на нескольких наборах входных данных (entry/stop/capital/risk).
2. **Фьючерс, ГО хватает**: `go_per_lot` мало относительно `available_margin_headroom`
   → `qty` не меняется относительно risk-based расчёта (новый cap не
   срабатывает).
3. **Фьючерс, ГО НЕ хватает даже на 1 лот**: `available_margin_headroom < go_per_lot`
   → `qty == 0`, лог с явной причиной (это тест на реальный инцидент BRU6 —
   в идеале с реальными числами BRU6 как regression-кейсом).
4. **Фьючерс, ГО хватает частично**: `risk_based_qty=25`, но `available_margin_headroom`
   позволяет только 10 лотов → `qty == 10` (min сработал корректно, не 25 и не 0).
5. **Отсутствие данных ГО** (`future_by` бросает исключение или `initial_margin_on_buy`
   пустой/нулевой) — см. решение fail-safe в п. (г) ниже, тест должен
   подтвердить именно ЭТО поведение, не молчаливый fallback на старую
   формулу без предупреждения.
6. **Граничный случай `available_margin_headroom <= 0`** (счёт уже на
   пределе маржи до этой сделки) → `qty == 0`, не отрицательное число и не
   деление на ноль.
7. **Округление**: `available_margin_headroom // go_per_lot` даёт дробный
   результат, близкий снизу к целому (например, 9.98 лота) — подтвердить,
   что `int()` округляет ВНИЗ (9, не 10) — переоценка здесь means реальные
   деньги, недооценка безопасна.

Дополнительно — **интеграционный тест на реальных исторических данных**:
прогнать `calc_quantity_from_risk()` с новой логикой на всех `trades.csv`
фьючерсных сделках in_sample/validation/holdout (уже есть в репозитории/
scratch), сравнить получившиеся `qty` с тем, что подразумевала текущая
(margin-агностичная) модель бэктеста — ожидаемое расхождение и есть та
самая "недооценка scarcity", которую мы измеряли всю сессию другим путём
(missed_profit%/margin_reject%) — если numbers не бьются в разумных
пределах, значит в реализации есть баг.

## г) Fail-open vs fail-safe — решение и обоснование

**Решение: fail-safe (блокировать вход), не fail-open.**

Обоснование: в отличие от `_is_crypto_futures_candidate()` (задача 2,
2026-08-13), где fail-open был оправдан тем, что `universe_builder.py` —
уже существующий ПЕРВИЧНЫЙ барьер, а новая проверка — ДОПОЛНИТЕЛЬНЫЙ
слой поверх него (отсутствие данных не увеличивает риск сверх уже
принятого базового уровня) — здесь **аналогичного первичного барьера
нет**. Текущая формула `calc_quantity_from_risk()` **уже баг** (не
учитывает ГО вообще) — если при отсутствии данных ГО откатываться на неё
"молча", это не поддержание существующей защиты, а точное воспроизведение
уже известного реального инцидента (BRU6) при каждом отсутствии данных.
Fail-safe здесь = "не пытаться посчитать риск-based qty вслепую, если не
можем проверить ГО" — то есть **явно отклонять вход с логом**, а не
занижать/завышать объём наугад.

Практическое следствие: если `future_by()` недоступен/падает у КОНКРЕТНОГО
инструмента систематически (не разовый сетевой сбой) — это будет громко
видно в логах (тот же паттерн громкого алерта, что и в
`dynamic_stop_manager.py`/`universe_builder.py` retry+alert), не тихо
"как повезёт".

## Оценка сложности/риска (сводка, без изменений от вчерашней оценки)

- Само ядро — небольшое (~20-30 строк + хелпер запроса ГО по образцу
  задачи 2). Но требует нового живого API-вызова внутри `trade_executor.py`
  (сейчас изолированный подпроцесс без состояния маржи от `auto_executor.py`)
  — не чисто точечный фикс по площади затрагиваемого кода.
- Риск рассинхрона: `auto_executor.py` проверяет `margin_ratio` В НАЧАЛЕ
  прохода по кандидату, `trade_executor.py` — независимо, доли секунды
  спустя, при реальном вызове. Два разных снимка одного состояния — не
  баг сам по себе (`trade_executor.py`'s проверка строже/точнее и является
  окончательной), но стоит явно залогировать оба числа при расхождении >
  небольшого порога, чтобы отличить "нормальный дрейф" от системной
  проблемы синхронизации.
- **Категория риска — реальные деньги, размер ордера.** Выше, чем
  крипто-фильтр или universe-фикс (которые могут только ОТКАЗАТЬ во
  входе, никогда не увеличить экспозицию по ошибке).

**Рекомендация не изменилась**: отдельная неспешная сессия, не сегодня.

## План dry-run периода перед полным доверием

1. **Mock-тесты (п. в) — обязательное условие ДО первого коммита в бой.**
2. После коммита — **включить логирование нового расчёта БЕЗ применения
   cap** (флаг вида `MARGIN_AWARE_SIZING_SHADOW_MODE=true`): считать и
   логировать, что сделал бы новый код, но реально исполнять по старой
   формуле — минимум **10 живых торговых дней** или **20 сигналов**,
   смотря что наступит раньше (при нынешней частоте ~1-3 сделки/день —
   это заметно больше недели наблюдения).
3. Сверить теневой лог: как часто новый cap реально сработал бы (`qty`
   отличался бы от старой формулы), было ли хоть раз `qty==0` (отказ),
   похоже ли распределение отличий на предсказанное бэктестом
   (missed_profit%/margin_reject% из сегодняшних N=30 таблиц) — если
   расхождение на порядок больше или меньше ожидаемого, разбираться
   ПРЕЖДЕ включения реального cap.
4. Только после этого — включить cap по-настоящему
   (`MARGIN_AWARE_SIZING_SHADOW_MODE=false`), с тем же уровнем внимания
   первую неделю, что был при включении `AUTO_EXECUTE_ENABLED=true`
   изначально (сверять логи вручную, не полагаться только на "тишину
   значит всё в порядке").
